# boostX — cPanel Deployment Guide (Staging)

End-to-end guide to deploy **both** projects on cPanel for the **staging** environment so the marketing site and CMS API work together.

| Project | Local path | Role |
|---------|------------|------|
| Frontend | `boostx.net` | Vite + React SPA (marketing site + `/super-admin` CMS UI) |
| Backend | `boostx.net-api` | Slim 4 + Doctrine API (auth, blogs, pricing, SEO files, uploads, leads) |

This guide targets staging hosts (not the live apex domain):

| Role | Hostname |
|------|----------|
| Marketing site | `https://staging.boostx.net` |
| API | `https://api-staging.boostx.net` |

> `api-staging.boostx.net` is used as a sibling subdomain of `boostx.net` (easier on cPanel than nested `api.staging.boostx.net`). You can rename the API host — just keep `VITE_API_URL` and `APP_URL` identical.

---

## 0. How the two projects bind (read this first)

Understanding these bindings avoids most staging failures.

```
Browser
  │
  ├─ https://staging.boostx.net       → React build (static files)
  │     │
  │     ├─ pages, /super-admin UI
  │     └─ fetch(VITE_API_URL + /api/...)   ← baked in at build time
  │
  └─ https://api-staging.boostx.net   → PHP API (document root = public/)
        ├─ /api/*                  → JSON API
        ├─ /uploads/blog/*         → uploaded images
        ├─ /robots.txt
        ├─ /sitemap.xml
        └─ /llms.txt
```

### Critical bindings

| Binding | Where | Staging value |
|---------|--------|----------------|
| `VITE_API_URL` | Frontend `.env` **before** `npm run build` | `https://api-staging.boostx.net` (no trailing slash preferred) |
| `APP_URL` | Backend `.env` | Same as API public URL, e.g. `https://api-staging.boostx.net` |
| `SITE_URL` | Backend `.env` | Marketing staging URL: `https://staging.boostx.net` |
| `CORS_ORIGINS` | Backend `.env` | Exact frontend origin: `https://staging.boostx.net` |
| `APP_ENV` | Backend `.env` | Prefer **not** `production` on staging so `robots.txt` stays `Disallow: /` (see note below) |
| `APP_DEBUG` | Backend `.env` | `false` (even on staging) |
| API document root | cPanel Domains | Must point at backend `public/` (not the repo root) |
| Uploads | `public/uploads/blog/` | Writable; URLs are built as `APP_URL + /uploads/blog/...` |
| Admin token | Browser `sessionStorage` | Sent as `Authorization: Bearer` and `X-Admin-Token` |

**Robots / indexing on staging:** `SeoService` only allows crawling when `APP_ENV=production`. For staging, keep `APP_ENV=staging` (or `local`) so search engines get `Disallow: /`. Set `APP_ENV=production` only when you intentionally want staging indexed (usually you do not).

### Important behaviors

1. **`VITE_API_URL` is compile-time.** Changing the API URL later requires rebuilding the frontend and re-uploading `dist/`.
2. **Frontend talks to the API host directly** (`src/lib/cmsApi.js`), not through Vite’s `/api` proxy (that proxy is **dev-only**).
3. **CORS must list the real staging origin.** Example: `https://staging.boostx.net`.
4. **`robots.txt` / `sitemap.xml` / `llms.txt` are generated by the API**, but `SITE_URL` points them at the **marketing staging domain**. You must proxy or redirect those three paths from `staging.boostx.net` to the API (covered below).
5. **`/admin-panel` is a marketing product page.** The CMS is **`/super-admin`**.

### Recommended hostname layout (staging)

| Hostname | Points to |
|----------|-----------|
| `staging.boostx.net` | Frontend `dist/` contents |
| `api-staging.boostx.net` | Backend app, document root = `.../boostx-api/public` |

Examples below use:

- Site: `https://staging.boostx.net`
- API: `https://api-staging.boostx.net`

## 1. Prerequisites (cPanel + local)

### On cPanel

- Parent domain `boostx.net` already on the account (needed to create subdomains)
- Ability to create **subdomains**
- Ability to change a domain’s **document root**
- **MySQL** databases
- **PHP 8.2+** (8.3/8.4 fine) with extensions: `pdo_mysql`, `json`, `mbstring`, `fileinfo`, `openssl`, `curl`
- **SSL** (AutoSSL / Let’s Encrypt)
- Prefer **SSH / Terminal** for `composer` and migrations (File Manager–only path is also documented)

### On your PC

- Node.js **18+** (20/22 recommended)
- Composer + PHP 8.2+ (only if you will build `vendor/` locally and upload it)
- Both project folders ready: `boostx.net` and `boostx.net-api`

## 2. Plan domains & DNS

### 2.1 Staging subdomain (frontend)

1. In cPanel → **Domains** (or **Subdomains**).
2. Create subdomain: `staging` on `boostx.net` → host **`staging.boostx.net`**.
3. Note its document root. cPanel often creates something like:

   ```text
   /home/USERNAME/staging.boostx.net
   ```

   or

   ```text
   /home/USERNAME/public_html/staging.boostx.net
   ```

   Use whatever path cPanel assigns; that folder is where you upload the Vite `dist/` contents.
4. Do **not** point the live apex `boostx.net` / `public_html` at this staging build unless you intend to replace production.

### 2.2 API subdomain

1. cPanel → **Domains** → **Create A New Domain** / **Subdomain**.
2. Create: `api-staging.boostx.net` (subdomain name `api-staging` on `boostx.net`).
3. Suggested app folder (outside the frontend root):

   ```text
   /home/USERNAME/boostx-api
   ```

4. Set the subdomain **document root** to:

   ```text
   /home/USERNAME/boostx-api/public
   ```

   This is required. If the document root is the repo root, `.env`, `src/`, and `vendor/` can be exposed.

### 2.3 DNS

If the domain uses external DNS (Cloudflare, etc.):

| Type | Name | Value |
|------|------|--------|
| A / CNAME | `staging` | Hosting IP / target |
| A / CNAME | `api-staging` | Same hosting IP / target |

Wait for DNS to propagate before issuing SSL.

### 2.4 SSL

1. cPanel → **SSL/TLS Status** (or Let’s Encrypt / AutoSSL).
2. Issue certificates for:
   - `staging.boostx.net`
   - `api-staging.boostx.net`
3. Force HTTPS for both hosts (cPanel “Force HTTPS Redirect” is fine).

## 3. Create the MySQL database

1. cPanel → **MySQL® Databases**.
2. Create database, e.g. `username_boostx_cms` (or `username_boostx_staging` if you want it clearly separate from a future prod DB).
3. Create a user with a strong password.
4. Add the user to the database with **ALL PRIVILEGES**.
5. Note the exact names cPanel shows (they are often prefixed), e.g.:

   ```text
   DB_NAME=username_boostx_cms
   DB_USER=username_boostx
   DB_PASS=********
   DB_HOST=localhost
   DB_PORT=3306
   ```

   Some hosts use `127.0.0.1` or a remote host string — use what cPanel lists under “MySQL hostname”.

## 4. Deploy the backend (API)

### 4.1 Upload the API code

Upload the **entire** `boostx.net-api` project into:

```text
/home/USERNAME/boostx-api
```

**Include:** `bin/`, `bootstrap/`, `config/`, `migrations/`, `public/`, `src/`, `composer.json`, `composer.lock`, `.env.example`

**Do not upload (or delete after):** local `.env` with localhost secrets, `body.txt`, IDE junk.

Ways to upload:

- File Manager → Zip → Upload → Extract
- FTP/SFTP
- Git (if the host supports it)

Expected layout:

```text
/home/USERNAME/boostx-api/
├── bin/
├── bootstrap/
├── config/
├── migrations/
├── public/          ← document root for api-staging.boostx.net
│   ├── .htaccess
│   ├── index.php
│   ├── router.php   ← local PHP built-in server only; Apache uses .htaccess
│   └── uploads/
│       └── blog/
├── src/
├── composer.json
├── composer.lock
└── .env             ← create on server (next step)
```

Confirm in cPanel that `api-staging.boostx.net` document root is `.../boostx-api/public`.

### 4.2 Create staging `.env`

In `/home/USERNAME/boostx-api/`:

1. Copy `.env.example` → `.env`
2. Edit values:

```env
APP_ENV=staging
APP_DEBUG=false
APP_URL=https://api-staging.boostx.net
SITE_URL=https://staging.boostx.net
DEFAULT_REGION_CODE=PK

DB_HOST=localhost
DB_PORT=3306
DB_NAME=username_boostx_cms
DB_USER=username_boostx
DB_PASS=YOUR_STRONG_DB_PASSWORD

CORS_ORIGINS=https://staging.boostx.net

TOKEN_TTL_SECONDS=604800
UPLOAD_MAX_BYTES=5242880

ADMIN_NAME="Super Admin"
ADMIN_EMAIL=admin@boostx.net
ADMIN_PASSWORD=CHANGE_ME_TO_A_STRONG_PASSWORD
```

Notes:

- `CORS_ORIGINS` must match the browser origin **exactly** (scheme + host, no path). No trailing slash.
- For this setup that is only `https://staging.boostx.net` (no `www` on the staging subdomain).
- `APP_URL` must be the public API base browsers can reach (used for upload absolute URLs).
- `SITE_URL` is used inside generated `robots.txt` / `sitemap.xml` / `llms.txt`.
- Keep `APP_ENV=staging` (not `production`) so staging is not openly crawlable.
- Change `ADMIN_PASSWORD` before seeding.

Protect `.env`:

- It must **not** live under the web document root (with document root = `public/`, you are fine).
- File permissions: roughly `600` or `640`.

### 4.3 Install PHP dependencies

**Option A — SSH / Terminal (preferred)**

```bash
cd ~/boostx-api
php -v          # confirm 8.2+
composer install --no-dev --optimize-autoloader
```

If `composer` is missing, use the host’s documented path or download `composer.phar`:

```bash
php composer.phar install --no-dev --optimize-autoloader
```

**Option B — No SSH**

1. On your PC (same PHP major if possible):

   ```bash
   cd boostx.net-api
   composer install --no-dev --optimize-autoloader
   ```

2. Zip and upload the `vendor/` folder to `~/boostx-api/vendor`.

### 4.4 PHP version & settings

1. cPanel → **MultiPHP Manager** (or **Select PHP Version**).
2. Set `api-staging.boostx.net` to **PHP 8.2+**.
3. Enable extensions if toggles exist: `pdo_mysql`, `mbstring`, `fileinfo`, `curl`, `openssl`, `json`.
4. Raise upload limits if needed (must be ≥ `UPLOAD_MAX_BYTES`, default 5MB):

   ```text
   upload_max_filesize = 8M
   post_max_size = 10M
   ```

### 4.5 Uploads directory permissions

```bash
mkdir -p ~/boostx-api/public/uploads/blog
chmod -R 755 ~/boostx-api/public/uploads
```

If uploads fail with permission errors, your host may need `775` and the correct owner/group (often your cPanel user). Keep the directory writable by PHP; do not make the whole app `777`.

### 4.6 Apache front controller

`public/.htaccess` should already contain:

```apache
RewriteEngine On
RewriteCond %{REQUEST_FILENAME} !-f
RewriteCond %{REQUEST_FILENAME} !-d
RewriteRule ^ index.php [QSA,L]
```

That sends non-file requests (all `/api/*`, SEO files) to Slim while still serving real files under `/uploads/...`.

If `mod_rewrite` is off or `AllowOverride` blocks `.htaccess`, ask the host to enable them — the API will not route correctly without this.

### 4.7 Run migrations & seeds

With SSH:

```bash
cd ~/boostx-api

php bin/console migrations:migrate --no-interaction

php bin/console app:seed-admin
php bin/console app:seed-seo
php bin/console app:seed-pricing
```

Without SSH:

- Some hosts offer “Run PHP script” / cron once — point a one-off cron at those commands, then disable it.
- Or run migrations from a trusted local machine **against the remote DB** only if the host allows remote MySQL (often blocked). Prefer SSH on the server.

Optional smoke check:

```bash
php bin/smoke-flow.php
```

(That script expects the API reachable as configured for local use; after deploy, prefer the HTTP health check below.)

### 4.8 Verify the API alone

Open / curl:

| Check | URL | Expect |
|-------|-----|--------|
| Health | `https://api-staging.boostx.net/api/health` | JSON OK |
| Pricing | `https://api-staging.boostx.net/api/pricing` | Plans JSON |
| Robots | `https://api-staging.boostx.net/robots.txt` | Text (`Disallow: /` when `APP_ENV` is not `production`) |
| Login | `POST https://api-staging.boostx.net/api/auth/login` | Token JSON |

Example login:

```bash
curl -X POST "https://api-staging.boostx.net/api/auth/login" \
  -H "Content-Type: application/json" \
  -d "{\"email\":\"admin@boostx.net\",\"password\":\"YOUR_ADMIN_PASSWORD\"}"
```

If health fails with 500, check:

- `.env` DB credentials
- `vendor/` installed
- PHP version / `pdo_mysql`
- cPanel **Errors** / `error_log` next to `public/`

## 5. Deploy the frontend (React / Vite)

### 5.1 Staging env (local machine)

In `boostx.net`, create `.env.production` (or `.env`) **before building**:

```env
VITE_API_URL=https://api-staging.boostx.net
```

Rules:

- Prefer **no trailing slash** (the app strips it, but keep it clean).
- Must be `https://` on the server.
- Must match `APP_URL` on the API.

### 5.2 Build locally

```bash
cd boostx.net
npm install
npm run build
```

Output folder: `dist/`

Contents typically include `index.html`, `assets/`, and files from `public/` (logos, favicons, etc.).

### 5.3 Upload `dist/` to the staging document root

Upload into the **`staging.boostx.net` document root** from step 2.1 (not the live `public_html` apex unless that *is* the staging root).

Example:

```text
/home/USERNAME/staging.boostx.net/
```

Upload the **contents** of `dist/`, not the `dist` folder itself.

Correct:

```text
staging.boostx.net/index.html
staging.boostx.net/assets/...
staging.boostx.net/images/...
```

Wrong:

```text
staging.boostx.net/dist/index.html   ← site would only work at /dist/
```

Backup any old files in that folder first.

### 5.4 SPA `.htaccess` (required for React Router)

React routes like `/pricing`, `/blog/some-post`, `/super-admin/posts` are client-side. Apache must fall back to `index.html`.

In the **staging** frontend document root, create or **append** to `.htaccess` (do not wipe existing cPanel PHP handler rules if present):

```apache
<IfModule mod_rewrite.c>
  RewriteEngine On
  RewriteBase /

  # --- SEO files live on the API; expose them on staging.boostx.net ---
  # Prefer proxy if your host allows [P]. Otherwise use redirects (R=302).
  # Proxy form (needs mod_proxy + host support):
  # RewriteRule ^(robots\.txt|sitemap\.xml|llms\.txt)$ https://api-staging.boostx.net/$1 [P,L]

  # Redirect form (works on most shared hosting):
  RewriteRule ^robots\.txt$ https://api-staging.boostx.net/robots.txt [R=302,L]
  RewriteRule ^sitemap\.xml$ https://api-staging.boostx.net/sitemap.xml [R=302,L]
  RewriteRule ^llms\.txt$ https://api-staging.boostx.net/llms.txt [R=302,L]

  # --- React SPA fallback ---
  RewriteRule ^index\.html$ - [L]
  RewriteCond %{REQUEST_FILENAME} !-f
  RewriteCond %{REQUEST_FILENAME} !-d
  RewriteCond %{REQUEST_FILENAME} !-l
  RewriteRule . /index.html [L]
</IfModule>
```

Why the SEO rules matter:

- Backend `SeoService` writes `Sitemap: https://staging.boostx.net/sitemap.xml` into robots when `SITE_URL=https://staging.boostx.net`.
- Those files are implemented as API routes, not static files in the Vite app.
- Locally, Vite proxies them; on staging you must bridge that gap on `staging.boostx.net`.

If your host supports a **Reverse Proxy** UI for those three paths, proxying is cleaner than redirects.

### 5.5 Verify the frontend

| Check | Expect |
|-------|--------|
| `https://staging.boostx.net` | Home page loads |
| `https://staging.boostx.net/pricing` | Pricing (hard refresh / direct URL) — proves SPA rewrite |
| `https://staging.boostx.net/super-admin` | Admin login screen |
| Browser DevTools → Network | API calls go to `https://api-staging.boostx.net/...` |
| Contact / Project Inquiry forms | Submit succeeds (CORS + API) |
| `https://staging.boostx.net/robots.txt` | Redirects/proxies to API robots |

## 6. Wire-up checklist (frontend ↔ API)

Work through this after both sides are live.

1. **API health** — `GET https://api-staging.boostx.net/api/health`
2. **CORS** — From `https://staging.boostx.net`, login or open Pricing. A CORS error means `CORS_ORIGINS` does not include that exact origin.
3. **Admin login** — `https://staging.boostx.net/super-admin` with seeded credentials.
4. **Uploads** — In admin, upload a blog image; confirm the returned URL starts with `https://api-staging.boostx.net/uploads/blog/` and the image opens.
5. **Pricing** — Public `/pricing` shows region plans from `GET /api/pricing`.
6. **Blog** — Publish a post; open `/blog/{slug}`.
7. **Leads** — Submit Contact + Project Inquiry; confirm rows in admin **Contact Messages** / **Request Join**.
8. **SEO** — Confirm robots on staging disallows crawling when `APP_ENV` is not `production`; sitemap/robots bridges from `staging.boostx.net` work.

## 7. Security hardening (do not skip)

- [ ] `APP_DEBUG=false`
- [ ] `APP_ENV=staging` (or anything other than `production` if you want staging de-indexed)
- [ ] Strong unique `ADMIN_PASSWORD` (change after first login if the seed used a known default)
- [ ] Strong unique DB password
- [ ] API document root is **`public/` only**
- [ ] `.env` not web-accessible
- [ ] HTTPS everywhere; HTTP → HTTPS redirects enabled
- [ ] `CORS_ORIGINS` is only `https://staging.boostx.net` (never `*` for admin flows)
- [ ] Uploads dir not executable as PHP if the host allows such hardening (images only; API already restricts MIME types)
- [ ] Remove local smoke files / unused debug scripts from the server if present
- [ ] Restrict cPanel/FTP access; keep backups
- [ ] Do not put staging credentials in public chats/repos

## 8. Updating later (redeploy)

### Backend code change

```bash
# upload changed files or git pull
cd ~/boostx-api
composer install --no-dev --optimize-autoloader
php bin/console migrations:migrate --no-interaction
```

Clear any opcode cache if the host provides one (sometimes MultiPHP / LiteSpeed cache).

### Frontend code or API URL change

```bash
# on your PC
# edit .env.production if API URL changed
npm run build
# replace staging.boostx.net document-root contents with new dist/
# keep .htaccess SEO + SPA rules
```

Remember: **any change to `VITE_API_URL` requires a new build.**

### Env-only API change

Edit `~/boostx-api/.env` (CORS, SITE_URL, etc.). No frontend rebuild needed unless the public API hostname changed.

## 9. Troubleshooting

| Symptom | Likely cause | Fix |
|---------|--------------|-----|
| Frontend loads but forms/admin fail with CORS | Origin missing / typo in `CORS_ORIGINS` | Must include exact `https://staging.boostx.net` |
| Admin API calls hit `127.0.0.1:8090` | Built without staging `VITE_API_URL` | Set env, rebuild, re-upload `dist/` |
| Direct `/pricing` URL → 404 | Missing SPA `.htaccess` | Add React fallback rules on staging root |
| `api-staging` returns 404 for `/api/health` | Document root not `public/`, or rewrite off | Fix domain root; confirm `.htaccess` |
| API 500 after deploy | DB creds, missing `vendor`, wrong PHP | Check `.env`, `composer install`, MultiPHP |
| `Lazy loading proxies require PHP 8.4` on migrate/console | Old `DoctrineFactory` always enabled native lazy objects | Use current `src/Support/DoctrineFactory.php` (gates native lazy objects to PHP ≥ 8.4). Or switch MultiPHP to **8.4** if available |
| `composer install` fails with packages requiring `php ^8.4` | Lock resolved on PHP 8.4 machine | Prefer MultiPHP **8.4** for CLI + `api-staging`, then reinstall; or regenerate lock with `--with-platform-php=8.2.35` |
| Images upload but don’t show | Wrong `APP_URL`, or uploads not writable | Fix `APP_URL`; fix `public/uploads/blog` perms |
| `robots.txt` on staging site is wrong / 404 | No proxy/redirect to API | Add rules in staging frontend `.htaccess` |
| Staging site is getting indexed | `APP_ENV=production` | Set `APP_ENV=staging` |
| Login works locally, fails on cPanel | Mixed content (`http` API on `https` site) | Use `https://api-staging...` in both `APP_URL` and `VITE_API_URL` |
| OPTIONS preflight fails | CORS middleware / host blocking | Confirm API responds 204 to OPTIONS; SSL and CORS headers present |

### Quick CORS debug

In DevTools → Network → failed request:

- Request **Origin** should be `https://staging.boostx.net`
- That value must appear in `CORS_ORIGINS`
- Response should include `Access-Control-Allow-Origin: https://staging.boostx.net`
- Allowed headers include `Authorization` and `X-Admin-Token` (already coded in `CorsMiddleware`)

## 11. End-to-end deployment order (short)

1. Create DNS/subdomains for `staging.boostx.net` + `api-staging.boostx.net`.
2. Create MySQL database/user.
3. Upload API → set document root to `public/` → create `.env` → `composer install` → migrate → seed.
4. Issue SSL for both hosts; force HTTPS.
5. Confirm `https://api-staging.boostx.net/api/health`.
6. Set frontend `VITE_API_URL` → `npm run build` → upload `dist/` into the **staging** document root → add SPA + SEO `.htaccess`.
7. Confirm CORS, admin login, upload, forms, pricing, blog, robots/sitemap bridge.
8. Harden (`APP_DEBUG=false`, `APP_ENV=staging`, strong passwords, backups).

Once that list is green, boostX staging is deployed on cPanel end-to-end.
